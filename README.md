# Agrobridge — мониторинг всходов (Трек 1.1)

Прототип: временной ряд NDVI/NDMI по контуру поля, выделение проблемных
периодов (отклонение от нормы сезона), карта, график, экспорт отчёта
в CSV / GeoJSON / PDF.

## Как запустить

```bash
cd agrobridge
pip install -r requirements.txt
streamlit run app.py
```

Откроется браузер на `http://localhost:8501`.

В сайдбаре выберите:
- **Demo (синтетические данные)** — работает мгновенно, без интернета,
  показывает реалистичную кривую сезона с искусственной "аномалией"
  в середине. Используйте это как основной сценарий на защите — надёжно.
- **Реальные данные (Sentinel Hub)** — настоящий запрос к Copernicus
  Data Space по вашему полю. Нужен интернет; первый запрос может занять
  10-30 секунд.

Свой контур поля можно загрузить файлом GeoJSON (Polygon или
FeatureCollection с одним полигоном) — например, нарисованным на
https://geojson.io.

## Структура проекта

| Файл | За что отвечает |
|---|---|
| `config.py` | Credentials, тестовый контур поля, параметры сезона и порог аномалии |
| `sentinel_client.py` | Запрос к Sentinel Hub Statistical API — получение NDVI/NDMI |
| `mock_data.py` | Синтетические данные для demo-режима |
| `analysis.py` | Расчёт нормы сезона, отклонений, флаг "проблемный период" |
| `export.py` | Экспорт отчёта в CSV / GeoJSON / PDF |
| `app.py` | Streamlit-интерфейс: карта, график, таблица, кнопки экспорта |

## Как объяснить логику на защите (коротко)

1. **NDVI/NDMI** — не наша выдумка, а стандартные спектральные индексы:
   NDVI = (NIR−RED)/(NIR+RED) показывает "живость" растительности,
   NDMI = (NIR−SWIR)/(NIR+SWIR) — её влажность.
2. Мы не скачиваем и не обрабатываем сами снимки — используем **Statistical
   API** Sentinel Hub: отправляем контур поля + формулу расчёта (evalscript),
   получаем готовую агрегированную статистику по датам. Это быстрее и не
   требует своего сервера для обработки растров — важно объяснить, почему
   это осознанный архитектурный выбор, а не "то, что получилось".
3. **"Норма сезона"** в текущей версии = среднее по всему ряду этого же поля
   за этот же сезон. Это самый простой и прозрачный baseline — специально
   выбран простым, чтобы можно было объяснить логику за 30 секунд, а не
   потому что не было времени на модель.
4. **Проблемный период** = отклонение текущего NDVI от нормы ниже порога
   (по умолчанию −15%). Порог настраивается в `config.py`.
5. Слой **SCL (Scene Classification Layer)** в evalscript отсекает облака,
   тени и снег — без этого в облачные дни индекс "проваливался" бы не
   из-за проблем с посевами, а из-за облаков. Это стоит явно упомянуть —
   показывает, что вы думали про качество данных, а не только про формулу.

## Вероятные вопросы жюри и как отвечать

**"Почему Statistical API, а не сами скачиваете снимки и не обрабатываете?"**
→ Для конкретного контура поля не нужен весь растр — не нужно скачивать и
хранить гигабайты снимков, Sentinel Hub уже агрегирует пиксели внутри
контура на своей стороне. Это быстрее и проще для прототипа за 4 дня;
для продакшена с сотнями полей это ещё и дешевле по трафику.

**"Как вы отличаете 'аномалию от засухи' от 'аномалии из-за облаков'?"**
→ SCL-маска отсекает облака/тени на уровне пикселя ещё до расчёта индекса,
плюс `sampleCount`/`valid_pixels` в ответе показывает, сколько пикселей
реально попало в расчёт — если их мало, доверие к точке ниже (это можно
показать в интерфейсе доп. фильтром, см. "что улучшить").

**"Норма сезона — это же просто среднее, разве это точно?"**
→ Да, сознательно простой baseline для прототипа. Правильное развитие —
сравнивать не со средним ЭТОГО же сезона, а со средним ЗА НЕСКОЛЬКО
ПРОШЛЫХ сезонов по этому же полю (историческая норма) — это и есть первое,
что мы бы сделали при развитии (см. ниже).

## AI-компонент (для критерия «Инновационность применения ИИ»)

Два компонента поверх временного ряда, оба в `ai_analysis.py`:

1. **Прогноз NDVI на 14 дней вперёд** — линейная регрессия (numpy.polyfit)
   по последним 5 наблюдениям + 90% доверительный интервал на основе
   остатков модели. Специально не взяли ARIMA/LSTM — сезон даёт всего
   15-18 точек, на таком объёме сложная модель либо не обучится, либо
   переобучится и даст неустойчивый прогноз. Простая, но честная модель —
   осознанный выбор, а не "не успели".
2. **Классификация типа аномалии** — правило-ориентированная логика по
   соотношению отклонений NDVI и NDMI: оба просели → засуха/суховей;
   NDVI просел, а NDMI в норме → возможна болезнь/вредитель (влага есть,
   а зелёная масса всё равно ниже); высокий разброс внутри контура →
   вероятная засорённость. Это не обученная ML-модель, а прозрачная
   эвристика с физическим обоснованием — на защите это стоит явно
   проговорить как сознательный выбор в пользу объяснимости.

**Вопрос жюри, который стоит ждать:** *"Это же не настоящий ML, а просто
if/else?"* → Да, классификация — экспертное правило, а не обученная модель;
прогноз — настоящая (пусть и простая) статистическая модель с параметрами,
оценёнными по данным. Ценность не в сложности алгоритма, а в том, что
решение объяснимо агроному и проверяемо в поле — в отличие от чёрного ящика.

## Проверка координат поля перед защитой

Если контур поля на карте похож на город/дорогу/лес — переключите базовую
карту в geojson.io на **Satellite** (не Streets!) при рисовании контура,
и в QGIS добавьте слой XYZ Tiles → Google/Bing Satellite поверх контура,
чтобы визуально свериться. Текущий `DEFAULT_FIELD_GEOJSON` в `config.py` —
грубый прямоугольник в Буландынском районе, а не обведённая по снимку
реальная граница — замените его на настоящий контур перед защитой.

## Что улучшить дальше (если будет время)

1. **Историческая норма** вместо среднего по текущему сезону — тянуть
   NDVI за 2-3 прошлых года по тому же полю и сравнивать с ними
   (честнее оценивает "хуже обычного").
2. **Несколько полей одновременно** — сейчас интерфейс на одно поле,
   легко расширить до списка/загрузки shapefile с несколькими контурами.
3. **Растровая карта индекса**, а не просто заливка контура одним цветом —
   показать NDVI как heatmap внутри поля (какие именно зоны просели),
   через Sentinel Hub Process API (не Statistical) с реальным растром.
4. **Уведомления** — при появлении новой аномалии отправлять сообщение
   в Telegram/на email агроному (задача близка к 2.2 из трека погоды).
5. **Фильтр по количеству валидных пикселей** — прятать из графика точки,
   где облачность съела почти все данные (низкий `valid_pixels`).
